## 1. 项目背景与目标

### 1.1 背景

随着移动端应用自动化需求的增长，测试人员、开发者和普通用户需要在PC端对手机进行远程控制，并通过脚本实现自动化操作（如自动化测试、游戏挂机、日常任务自动化等）。

### 1.2 目标

开发一款跨平台的手机投屏管理软件，支持 **Windows 与 macOS**，实现低延迟投屏、键鼠模拟交互、强大的脚本录制与管理功能，并通过机器人通知将运行结果同步至团队协作软件。

## 2. 产品范围 (V1.0)

- **平台支持**：Windows 10/11 (x64) 与 macOS 11+ (Intel/Apple Silicon)
- **移动端**：Android 10+ (基于ADB协议)
- **连接方式**：USB连接（优先），无线Wi-Fi连接（后续支持）
- **设备数量**：单设备连接

#### 3.7.1 技术方案

| **层级** | **技术选型** | **说明** |
| :--- | :--- | :--- |
| AI编排框架 | LangGraph.js | 使用LangGraph的Node.js版本（@langchain/langgraph）构建有状态的工作流，管理多步骤推理与工具调用 |
| 视觉模型 | 智谱GLM-4V | 通过HTTP API调用智谱多模态大模型，对手机屏幕截图进行视觉理解，识别UI元素位置和文本内容 |
| 大语言模型 | DeepSeek Chat | 在意图理解和指令解析环节使用DeepSeek Chat模型，将用户自然语言解析为结构化动作参数 |
| 录制的点击模板 | RecordedClick（TypeORM + SQLite） | 录制的点击事件作为动态工具注入AI提示词，AI可优先使用已录制的坐标 |
| 命令执行适配层 | ADB Shell | 将解析后的动作（tap、swipe、input text等）通过ADB发送至设备执行 |

#### 3.7.2 工作流设计（LangGraph Agent）

```
用户输入 → [意图理解节点(LLM)]
                    │
          ┌─────────┴─────────┐
          ▼                    ▼
    [坐标类指令]           [纯按键指令/check_text]
          │                    │
          ▼                    │
   [截屏节点(ADB)]            │
          │                    │
          ▼                    │
   [视觉检测节点(VLM)]        │
    (检查屏幕上是否有指定     │
     文本/元素)               │
          │                    │
          └─────────┬─────────┘
                    ▼
           [步骤转换节点]
                    │
                    ▼
      ┌─────────────────────┐
      │  AI执行引擎          │
      │  (遍历步骤逐条执行)   │
      └─────────────────────┘
```

**实际工作流路由逻辑**：

| 条件 | 路径 | 说明 |
| :--- | :--- | :--- |
| 指令包含`check_text` | 意图解析 → 截图 → 视觉检测 → 步骤转换 | 需要视觉模型验证文本是否存在 |
| 指令需要坐标（点击/滑动等） | 意图解析 → 步骤转换（直接使用已录制的点击坐标或LLM返回坐标） | 不需要视觉检测，直接执行 |
| 纯按键指令（回主屏幕/返回） | 意图解析 → 步骤转换 | 跳过截图和视觉分析 |

**各节点职责**：

| **节点名称** | **输入** | **处理逻辑** | **输出** |
| :--- | :--- | :--- | :--- |
| **意图理解** | 用户自然语言指令 | 调用DeepSeek Chat分析指令意图，提取动作类型和参数；配合已录制的点击模板作为动态工具，AI可引用已有坐标 | 结构化意图对象（支持多步骤sequence） |
| **截屏** | 设备serial | 调用ADB截取当前手机屏幕，保存为Base64图像 | 屏幕截图Base64 |
| **视觉检测** | 屏幕截图 + 目标描述 | 调用智谱GLM-4V多模态模型，检测屏幕上是否包含指定文本/元素 | 检测结果（是否匹配+描述） |
| **步骤转换** | 意图对象 + 检测结果 | 将AI解析结果映射为EngineStep[] | 引擎步骤列表 |
| **引擎执行** | 引擎步骤列表 | 遍历步骤，调用StepExecutor逐条执行 | 执行结果 |

#### 3.7.3 典型场景示例

| **用户指令** | **意图理解结果** | **执行步骤序列** |
| :--- | :--- | :--- |
| "点击微信" | `{ action: "tap", target: "微信", ... }` | 使用已录制坐标或LLM返回坐标 → `input tap x y` |
| "滑动到下一屏" | `{ action: "swipe", params:{direction:"left"} }` | 计算中心坐标 → `input swipe x1 y1 x2 y2 300` |
| "回主屏幕" | `{ action: "keyEvent", params:{key:"HOME"} }` | `input keyevent KEYCODE_HOME` |
| "打开微信，进入陈晓蓓聊天，输入Hello，发送" | `{ action: "sequence", steps: [openApp, tap, type, tap] }` | 打开微信 → 点击联系人 → 输入文本 → 点击发送（4步连续执行） |
| "检查屏幕是否包含'发送'按钮" | `{ action: "check_text", target: "发送" }` | 截图 → 调用GLM-4V检测 → 返回是否匹配 |

#### 3.7.4 关键技术难点与对策

1. **动态UI适配**
   - *难点*：不同App、不同版本的UI布局差异巨大，AI可能误判。
   - *对策*：提供录制的点击模板作为动态工具，AI优先使用已录制的坐标；同时支持用户手动录制并命名，提高准确率。

2. **执行时序与动效等待**
   - *难点*：执行步骤后界面动效未完成（如页面切换动画），导致下一步操作位置错误。
   - *对策*：步骤间默认间隔3秒（可配置），AI解析的连续操作间自动插入延迟。

3. **多步骤复合指令**
   - *难点*：用户一条指令可能包含多个操作（"打开微信，发送消息"），需要分解为多步并处理依赖关系。
   - *对策*：意图解析阶段支持`sequence`类型，将复合指令拆分为多步IntentResult，步骤转换时逐条映射为EngineStep[]并顺序执行。

4. **模型调用成本**
   - *难点*：频繁调用大模型API会产生较高费用和延迟。
   - *对策*：录制的点击模板作为工具优先使用，仅在复杂场景（如check_text）调用视觉模型。纯按键指令（home/back）完全不调用模型。

#### 3.8.2 交互流程

**流程一：手动录制点击**

```
用户点击录制按钮 → 投屏区域覆盖半透明蒙版 → 鼠标变为十字准星(crosshair)
  → 用户在蒙版上点击目标位置 → 弹出表单弹窗
  → 表单自动填入：坐标(x,y) = 点击位置、type = "click"
  → 用户填写名称（如"点击微信"）→ 点击保存
  → 数据写入 recorded_clicks 表 → 关闭弹窗 → 退出录制模式
```

**流程二：查看与管理录制模板**

```
用户点击查看按钮 → 弹出录制模板列表弹窗
  → 列表分页展示（每页10条），显示：名称、坐标、类型、创建时间
  → 每条记录右侧有「编辑」「删除」操作按钮
  → 编辑：弹出编辑弹窗，可修改名称
  → 删除：确认后删除该记录
```

#### 3.8.4 录制模式详细行为

| **场景** | **行为** |
| :--- | :--- |
| 点击录制按钮（未激活） | 激活录制模式：投屏区域覆盖半透明蒙版（z-index高于画布但低于工具栏），鼠标变为 `cursor: crosshair`，录制按钮高亮 |
| 点击录制按钮（已激活） | 退出录制模式：移除蒙版，恢复鼠标样式，录制按钮恢复正常 |

| 点击取消 | 关闭弹窗，**保持**录制模式（用户可继续点击其他位置录制） |
| 按 Escape 键 | 退出录制模式（移除蒙版） |

#### 3.8.6 模板复用入口

录制的点击模板在以下两个场景中可供选择使用：

1. **AI智能操控（F-18→F-20）**：AI助手在执行"点击微信"等指令时，优先查询 `recorded_clicks` 表中名称匹配的模板，直接使用其坐标执行，无需调用VLM视觉分析，提升响应速度和降低API成本。
2. **添加脚本步骤**：在 `NewStepDialog` 新增步骤时，增加"从录制模板选择"选项，打开录制模板列表弹窗，选中后自动填充步骤参数（type=click, x, y）。

| 数据持久化 | SQLite (TypeORM + better-sqlite3) | 与脚本管理共用同一数据库实例、同一 DataSource |
| 实体定义 | TypeORM Entity (`RecordedClickEntity`) | 注册到 `AppDataSource`，DDL 同步到数据源初始化流程 |
| IPC通信 | Electron ipcMain.handle / ipcRenderer.invoke | 遵循现有脚本模块的 IPC 模式 |
| 前端UI | React + Tailwind CSS + shadcn/ui | 复用项目中已有的 Button、Dialog、Input 等组件 |
| 图标 | lucide-react | 录制使用 `CircleDot` 或 `Radio`，查看使用 `List` |

## 5. 附录：技术实现建议

### 5.1 核心技术选型建议

- **投屏核心**：使用 **scrcpy** (v4.0+) 作为底层服务。其本身支持Windows和macOS双平台，可大幅降低跨平台开发成本。
- **交互控制**：利用 scrcpy 的 `--hid-mouse` 和 `--hid-keyboard` 参数实现HID模拟。此模式将电脑鼠标模拟为“物理外挂”，兼容性最佳。
- **脚本引擎**：使用 **微软的 ClearScript** (V8引擎) 或 **Node.js** 嵌入式版本来运行JavaScript。
- **跨平台UI框架**：
  - **Qt (C++)**：scrcpy原生基于Qt，集成度高，资源占用低，推荐使用。
  - **Electron (Web技术)**：开发效率高但内存占用较高，macOS上体验尚可。
  - **Flutter**：桌面端支持正在成熟，也可考虑。

### 5.2 跨平台注意事项

- **ADB工具路径**：Windows使用`adb.exe`，macOS使用`adb`（需处理权限`chmod +x`）。软件需自动识别操作系统并调用对应可执行文件。
- **USB权限**：macOS无需驱动但可能需要用户授权“屏幕录制”权限才能捕获输入；Windows需要正确的ADB驱动。
- **窗口管理**：双平台窗口API不同，使用Qt可统一抽象层。

### 5.3 难点攻克与参考

1. **坐标适配问题**
   - 手机分辨率与PC窗口分辨率不同。脚本录制的坐标必须是 **相对坐标**（例如 `0.5, 0.5` 代表屏幕中心），执行时再根据当前设备分辨率换算为绝对坐标，否则换手机后脚本会失效。

2. **即时通讯机器人格式差异**
   - 虽然都叫Webhook，但飞书、钉钉、微信的JSON结构完全不同。
   - *建议*：开发一个 **“通知适配层”** 。用户选择“飞书”后，软件自动套用对应的MsgType模板，仅需用户填写密钥。

3. **连接稳定性**
   - ADB连接容易因手机锁屏、USB线松动断开。
   - *建议*：实现 **守护进程**。通过读取 `adb devices` 状态，发现设备离线自动重连（`adb reconnect`），确保无人值守的自动化任务能够7x24小时运行。
