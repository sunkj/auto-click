## 1. 项目背景与目标

### 1.1 背景

随着移动端应用自动化需求的增长，测试人员、开发者和普通用户需要在PC端对手机进行远程控制，并通过脚本实现自动化操作（如自动化测试、游戏挂机、日常任务自动化等）。

### 1.2 目标

开发一款跨平台的手机投屏管理软件，支持 **Windows 与 macOS**，实现低延迟投屏、键鼠模拟交互、强大的脚本录制与管理功能，并通过机器人通知将运行结果同步至团队协作软件。

## 2. 产品范围 (V1.0)

- **平台支持**：Windows 10/11 (x64) 与 macOS 11+ (Intel/Apple Silicon)
- **移动端**：Android 10+ (基于ADB协议)
- **连接方式**：USB连接（优先），无线Wi-Fi连接（后续支持）
- **设备数量**：单设备连接

#### 3.7.1 技术方案

| **层级** | **技术选型** | **说明** |
| :--- | :--- | :--- |
| AI编排框架 | LangGraph.js | 使用LangGraph的Node.js版本（@langchain/langgraph）构建有状态、有环的Agent工作流，管理多步骤推理与工具调用 |
| 视觉模型 | DeepSeek多模态（deepseek-vision） | 通过API调用DeepSeek的多模态大模型，对手机屏幕截图进行视觉理解，识别UI元素位置、文本内容和控件类型 |
| 大语言模型 | DeepSeek Chat | 在意图理解和指令解析环节使用DeepSeek Chat模型，将用户自然语言解析为结构化动作参数 |
| 命令执行适配层 | ADB Shell | 将解析后的动作（tap/x/y、swipe/x1/y1/x2/y2/duration、input text等）通过ADB发送至设备执行 |

#### 3.7.2 工作流设计（LangGraph Agent）

```
用户输入 → [意图理解节点(LLM)] → [截屏节点] → [视觉分析节点(VLM)] 
                                                      ↓
用户确认 ← [人工确认节点(可选)] ← [坐标映射节点] ← [坐标计算与元素定位]
                                                      ↓
                                              [命令生成节点] → [ADB执行节点] → 反馈结果
```

**各节点职责**：

| **节点名称** | **输入** | **处理逻辑** | **输出** |
| :--- | :--- | :--- | :--- |
| **意图理解** | 用户自然语言指令 | 调用DeepSeek Chat分析指令意图，提取动作类型（click/swipe/longPress/input/back/home）和目标语义描述 | 结构化动作对象 `{ action, target, params }` |
| **截屏** | — | 调用ADB截取当前手机屏幕，保存为Base64图像 | 屏幕截图Base64 |
| **视觉分析** | 屏幕截图 + 目标语义描述 | 调用DeepSeek多模态模型，识别目标元素在屏幕上的坐标位置及所在区域 | 目标元素坐标及区域描述 |
| **坐标映射** | 目标坐标 + 设备分辨率 | 将VLM返回的坐标根据当前设备分辨率进行校准，支持相对坐标和绝对坐标转换 | 校准后的精确坐标与动作参数 |
| **人工确认**（可选） | 指令意图 + 目标截图 + 预执行动作 | 在敏感操作前暂停，向用户展示即将执行的动作，等待确认/取消/修正 | 用户确认结果 |
| **命令生成** | 校准坐标 + 动作类型 | 根据动作类型生成对应的ADB shell命令参数 | ADB命令参数 |
| **ADB执行** | ADB命令参数 | 通过ADB子进程执行命令，返回执行结果 | 执行成功/失败 + 执行后截图 |

#### 3.7.3 典型场景示例

| **用户指令** | **意图理解结果** | **视觉识别目标** | **生成的ADB命令** |
| :--- | :--- | :--- | :--- |
| "点击微信" | `{ action: "tap", target: "微信图标" }` | 在屏幕底部或桌面区域识别"微信"图标的位置 (x, y) | `input tap x y` |
| "滑动到下一屏" | `{ action: "swipe", target: "桌面", params:{direction:"left"} }` | 识别桌面边缘起始坐标 | `input swipe x1 y1 x2 y2 300` |
| "长按支付宝" | `{ action: "longPress", target: "支付宝图标" }` | 识别支付宝图标位置 (x, y) | `input swipe x y x y 1500` |
| "返回桌面" | `{ action: "keyEvent", target: "HOME" }` | 无需视觉识别 | `input keyevent KEYCODE_HOME` |
| "打开设置并点击WiFi" | `{ action: "sequence", steps: [...] }` | 步骤1：识别"设置"图标；步骤2：识别"WiFi"菜单项 | 多步命令序列 |

#### 3.7.4 关键技术难点与对策

1. **动态UI适配**
   - *难点*：不同App、不同版本的UI布局差异巨大，VLM可能误判元素位置。
   - *对策*：在视觉分析节点中加入历史截图缓存，对同一App的同一界面做坐标修正；支持用户手动拖拽校准并记忆校正结果。

2. **执行时序与动效等待**
   - *难点*：点击后界面动效未完成（如页面切换动画），导致下一步视觉分析截取到过渡帧。
   - *对策*：在每个命令执行后加入自适应等待节点，持续截屏对比变化，直至界面稳定后再进入下一轮视觉分析。

3. **多轮对话上下文**
   - *难点*：用户连续指令（如"点这里"→"再往下滑一点"）依赖屏幕状态的历史上下文。
   - *对策*：LangGraph工作流节点间维护 `ScreenState` 对象，记录上一帧截图、已执行动作序列和当前界面上下文摘要。

4. **模型调用成本**
   - *难点*：频繁调用DeepSeek多模态API会产生较高费用和延迟。
   - *对策*：引入轻量级本地预判断（如OCR识别文本+模板匹配定位常见图标），仅在复杂场景或匹配失败时回退到VLM调用。

#### 3.8.1 数据模型

点击录制数据存储于独立的 `recorded_clicks` 表，与脚本步骤表（`steps`）解耦，作为跨功能的公用模板库。

| **字段** | **类型** | **说明** |
| :--- | :--- | :--- |
| `id` | INTEGER (PK, AUTOINCREMENT) | 自增主键 |
| `name` | TEXT | 用户自定义名称，如"点击微信"、"点击支付宝" |
| `x` | INTEGER | 点击坐标 X（设备物理像素） |
| `y` | INTEGER | 点击坐标 Y（设备物理像素） |
| `type` | TEXT | 动作类型，固定为 `"click"`（预留后续扩展 swipe、longpress 等） |
| `created_at` | DATETIME | 创建时间 |
| `updated_at` | DATETIME | 更新时间 |

#### 3.8.2 交互流程

**流程一：手动录制点击**

```
用户点击录制按钮 → 投屏区域覆盖半透明蒙版 → 鼠标变为十字准星(crosshair)
  → 用户在蒙版上点击目标位置 → 弹出表单弹窗
  → 表单自动填入：坐标(x,y) = 点击位置、type = "click"
  → 用户填写名称（如"点击微信"）→ 点击保存
  → 数据写入 recorded_clicks 表 → 关闭弹窗 → 退出录制模式
```

**流程二：查看与管理录制模板**

```
用户点击查看按钮 → 弹出录制模板列表弹窗
  → 列表分页展示（每页10条），显示：名称、坐标、类型、创建时间
  → 每条记录右侧有「编辑」「删除」操作按钮
  → 编辑：弹出编辑弹窗，可修改名称
  → 删除：确认后删除该记录
```

#### 3.8.4 录制模式详细行为

| **场景** | **行为** |
| :--- | :--- |
| 点击录制按钮（未激活） | 激活录制模式：投屏区域覆盖半透明蒙版（z-index高于画布但低于工具栏），鼠标变为 `cursor: crosshair`，录制按钮高亮 |
| 点击录制按钮（已激活） | 退出录制模式：移除蒙版，恢复鼠标样式，录制按钮恢复正常 |
| 在蒙版区域点击 | 阻止事件穿透到下方画布，解析点击位置的设备物理坐标，弹出表单弹窗 |
| 点击保存 | 校验名称非空 → 写入数据库 → 关闭弹窗 → 退出录制模式 → 若写入失败显示错误提示 |
| 点击取消 | 关闭弹窗，**保持**录制模式（用户可继续点击其他位置录制） |
| 按 Escape 键 | 退出录制模式（移除蒙版） |

#### 3.8.6 模板复用入口

录制的点击模板在以下两个场景中可供选择使用：

1. **AI智能操控（F-18→F-20）**：AI助手在执行"点击微信"等指令时，优先查询 `recorded_clicks` 表中名称匹配的模板，直接使用其坐标执行，无需调用VLM视觉分析，提升响应速度和降低API成本。
2. **添加脚本步骤**：在 `NewStepDialog` 新增步骤时，增加"从录制模板选择"选项，打开录制模板列表弹窗，选中后自动填充步骤参数（type=click, x, y）。

## 5. 附录：技术实现建议

### 5.1 核心技术选型建议

- **投屏核心**：使用 **scrcpy** (v4.0+) 作为底层服务。其本身支持Windows和macOS双平台，可大幅降低跨平台开发成本。
- **交互控制**：利用 scrcpy 的 `--hid-mouse` 和 `--hid-keyboard` 参数实现HID模拟。此模式将电脑鼠标模拟为“物理外挂”，兼容性最佳。
- **脚本引擎**：使用 **微软的 ClearScript** (V8引擎) 或 **Node.js** 嵌入式版本来运行JavaScript。
- **跨平台UI框架**：
  - **Qt (C++)**：scrcpy原生基于Qt，集成度高，资源占用低，推荐使用。
  - **Electron (Web技术)**：开发效率高但内存占用较高，macOS上体验尚可。
  - **Flutter**：桌面端支持正在成熟，也可考虑。

### 5.2 跨平台注意事项

- **ADB工具路径**：Windows使用`adb.exe`，macOS使用`adb`（需处理权限`chmod +x`）。软件需自动识别操作系统并调用对应可执行文件。
- **USB权限**：macOS无需驱动但可能需要用户授权“屏幕录制”权限才能捕获输入；Windows需要正确的ADB驱动。
- **窗口管理**：双平台窗口API不同，使用Qt可统一抽象层。

### 5.3 难点攻克与参考

1. **坐标适配问题**
   - 手机分辨率与PC窗口分辨率不同。脚本录制的坐标必须是 **相对坐标**（例如 `0.5, 0.5` 代表屏幕中心），执行时再根据当前设备分辨率换算为绝对坐标，否则换手机后脚本会失效。

2. **即时通讯机器人格式差异**
   - 虽然都叫Webhook，但飞书、钉钉、微信的JSON结构完全不同。
   - *建议*：开发一个 **“通知适配层”** 。用户选择“飞书”后，软件自动套用对应的MsgType模板，仅需用户填写密钥。

3. **连接稳定性**
   - ADB连接容易因手机锁屏、USB线松动断开。
   - *建议*：实现 **守护进程**。通过读取 `adb devices` 状态，发现设备离线自动重连（`adb reconnect`），确保无人值守的自动化任务能够7x24小时运行。
